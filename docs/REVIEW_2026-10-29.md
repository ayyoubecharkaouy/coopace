Ce bilan précède l'essai natif ICMP/TCP réussi et consigné ensuite dans [VALIDATION_VIRTUAL_LAB_2026-10-29.md](VALIDATION_VIRTUAL_LAB_2026-10-29.md). Ses constats « à confirmer » décrivent l'état à l'instant de la revue.

## Décision de poursuite

Le socle permet de poursuivre l'étape 4.2. La prochaine activité est la validation native du laboratoire ICMP/TCP sur Linux, avant d'étendre le scénario à une charge contrôlée. L'étape 4.2 reste ouverte ; la gestion des files, la restauration d'une passerelle réelle et les décisions de l'étape 5 ne sont pas encore validées.

Cette revue porte sur le rapport V5 fourni au démarrage, la documentation courante, les frontières du code et les vérifications reproduites ci-dessous. Elle inclut les livraisons du laboratoire virtuel et un correctif de nettoyage. Elle n'est pas une preuve de fonctionnement sur le réseau du foyer ou sur toutes les plateformes.

## Cohérence avec le rapport V5

Les responsabilités restent alignées sur « Edge & Peers » : une passerelle pour le trafic qui la traverse, des agents volontaires et des consentements distincts. Le logiciel n'intercepte pas le contenu TLS, ne promet pas de capacité WAN supplémentaire et ne présente pas la coordination comme une amélioration déjà mesurée.

Le rapport donne la priorité à l'instrumentation et à un moteur existant mesurable, avec comparaison à CAKE/SQM, avant l'automatisation ou le ML. Le socle de groupe déjà développé prépare les observations ; il n'est pas nécessaire de l'étendre à tous les appareils avant de poursuivre le prototype de passerelle. La suite doit maintenant produire des résultats expérimentaux.

## Défaut reproduit et corrigé

Le script du laboratoire traitait immédiatement SIGTERM après `ip netns add`. Si la commande avait réussi juste avant le signal, le shell pouvait exécuter le nettoyage avant l'affectation du drapeau de création. L'espace nouveau n'était alors pas supprimé, malgré un journal de nettoyage apparemment réussi.

Un test avec de faux outils a reproduit le défaut pour chacun des trois espaces : client, passerelle et serveur. Le correctif diffère les interruptions gérées pendant la création, enregistre la ressource, puis déclenche la sortie demandée. Le même mécanisme protège l'enregistrement du PID du serveur TCP. Le nettoyage ignore les interruptions gérées supplémentaires pendant sa tentative et conserve le code du signal initial.

Le test de régression vérifie maintenant le code `143`, la sortie JSON vide, la suppression des ressources simulées et du répertoire temporaire. Les tests de collision, d'erreur et d'arrêt du serveur restent réussis. SIGKILL, une panne machine ou une erreur système ne permettent toujours pas de garantir le nettoyage ; la récupération ciblée reste décrite dans [VIRTUAL_LAB.md](VIRTUAL_LAB.md).

## Vérifications reproduites

- Suite Go complète sans réutiliser le cache de tests, formatage, analyse statique et compilation Linux : réussite.
- Compilation et analyse statique de tous les paquets pour Windows amd64, sans CGO : réussite.
- Tests du groupe et de la cible TCP avec `-race` : réussite.
- Suite Python : 14 tests réussis après correction, avec outils simulés et sans création de réseau réel.
- Syntaxe des trois scripts shell et différences Git : contrôlées.
- Lancement Linux de `coopace status`, `coopace observe`, de l'aide de la cible TCP et du diagnostic JSON : réussite.
- Frontières d'importation, liens Markdown locaux et exclusion des états locaux et clés générées de Git : contrôlées.

Le diagnostic exécuté indique `partial: true`, `scope: process_network_namespace`, `traffic_coverage: unverified` et `restoration: not_implemented`. Il n'est pas enregistré comme un inventaire réel du foyer.

Trois tests sont explicitement ignorés ici car les sockets sont interdites : `TestProbeLoopbackConnectsAndClosesWithoutPayload`, `TestGroupLoopbackExchange` et `TestLoopbackEndpoint`. Un résultat global réussi comprenant ces exclusions ne valide pas leurs connexions réelles. Les répertoires `.local/experiments`, `.local/baselines` et `.local/gateway-reports` sont absents au moment de cette revue ; aucune nouvelle mesure de terrain n'est déduite des tests.

## Prochaine activité et conditions de passage

1. Sur le Linux de laboratoire, vérifier la cible TCP en boucle locale, puis exécuter les modes `run` et `run-tcp` selon [VIRTUAL_LAB.md](VIRTUAL_LAB.md). Conserver les codes de sortie, journaux, rapports et commit utilisé. Vérifier le nettoyage des seuls noms inscrits dans le journal, sans suppression globale.
2. Une fois ce chemin natif vérifié, préparer une charge contrôlée et des séries répétées avec les paramètres et critères définis avant l'expérience. Le petit rapport TCP `unspecified` actuel n'est pas une référence `idle`/`loaded`.
3. Avant une première politique de files, fixer le périmètre d'intervention et développer puis tester une restauration indépendante du pilotage. La comparaison devra distinguer l'état initial, le moteur configuré manuellement et Coopace sans ML.

Les validations natives du groupe et de Windows restent à solder séparément ; elles n'imposent pas d'élargir le périmètre avant l'essai de passerelle Linux. Pour vérifier les sockets locales hors de cet environnement :

```sh
sh scripts/go.sh test -count=1 -v -run '^TestLoopbackEndpoint$' ./scripts/lab-tcp
sh scripts/go.sh test -count=1 -v -run '^TestGroupLoopbackExchange$' ./apps/agent/internal/group
```

Chaque cas doit afficher `PASS`, sans `SKIP`, pour être consigné comme exécuté. Ces essais locaux ne remplacent pas le laboratoire routé ni un essai entre appareils physiques. La [feuille de route](ROADMAP.md) et le [protocole de référence](GATEWAY_BASELINE.md) restent les critères de clôture de l'étape 4.2.
